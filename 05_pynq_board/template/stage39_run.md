# Stage39 板端运行与物理验收

板端包修订号：`stage39-board-20261008-import-notebook-r2`。此版本固定按绝对路径加载
`software/stage5/n2_stream.py`，并且 Notebook 校验忽略 Jupyter 自动写入的执行次数、
输出和界面元数据，同时仍严格校验六个单元格的类型、顺序和源代码。

## 1. 上传与启动

1. 删除 Jupyter 中旧的同名文件夹和旧 ZIP，把整个 `N2-NeRF2-Stage39-board-20261008-r2.zip`
   上传到 PYNQ-Z2，并解压为
   `/home/xilinx/jupyter_notebooks/N2-NeRF2-Stage39-board`。不要覆盖 Stage37 或 Stage38。
2. 冷启动 PYNQ-Z2，确认电脑能打开 `http://192.168.2.99:9090`。
3. 打开 `Stage39_QAT_Four_Scenes.ipynb`，严格按单元格顺序运行。
4. 第 1 单元格逐文件检查上传是否完整。普通文件执行逐字节 SHA-256 校验；Notebook
   校验单元格类型、顺序和源内容，允许 Jupyter 正常写入执行次数、输出和界面元数据。
   第 2 单元格启动独立受监督服务后会返回，不需要保持 Notebook 单元格运行，关闭
   浏览器标签也不会停止服务。

## 2. Stage39.2：四场景物理逐位一致性

运行第 3 单元格。它在同一份 95 MHz 位流上依次加载 s23、Meetingroom、Office1、
Office2 的 QAT 运行时权重和固定 Rx 缓存，每个场景计算一幅完整 90×360 空间谱。
每幅图的 32,400 个原始 Q15 像素都会生成 SHA-256，并与独立可移植整数参考比较。
四个场景都必须显示 `PASS`。

## 3. Stage39.3：50 次时延和稳定性

运行第 4 单元格。每个场景连续计算 50 幅完整空间谱，共 200 幅。验收条件为：

- 每场景 50 次结果的原始 Q15 哈希保持一致；
- 每次结果与可移植整数参考一致；
- 每场景中位数不超过 1.2 s；
- 每场景 P95 不超过 1.5 s。

这里统计的是完整 90×360、32,400 条射线、每条 64 个采样点的 FPGA 核心推理时间，
不包含 HTTP、浏览器绘图和 HDMI 上传时间。

## 4. 四场景完整 test 集

在电脑端 App 中分别选择四个场景并运行“总体精度”。必须等待每个场景显示完整：
s23 1225 幅、Meetingroom 200 幅、Office1 200 幅、Office2 100 幅。中断后可续跑；
如果位流、运行时模型或测试目录发生变化，服务会归档旧证据并从 0 开始，避免旧结果
冒充 Stage39。

## 5. 导出真实板卡证据

完成第 3、4 单元格以及四场景总体精度后，运行第 5 单元格。下载它输出的：

`/home/xilinx/jupyter_notebooks/N2-NeRF2-Stage39-results/physical/stage39_physical_gate/Stage39_physical_evidence.zip`

压缩包包含逐文件 SHA-256、自检、50 次基准以及四场景完整测试摘要。电脑端最终验收器
会再次读取并逐项核对。第 6 单元格仅用于查看服务状态。

## 6. HDMI 与日常演示

启动电脑端 App 后，板端服务地址填写 `http://192.168.2.99:8311`。日常演示不必重复
50 次基准。HDMI 连接与否不影响计算；只有勾选 HDMI 显示时才加载视频位流。视频位流
显示结束后，下一次推理会自动恢复加速位流和当前场景运行时模型。

Stage39 的最终输出始终是原始 FPGA Q15 除以 32768，不存在输出 calibration。四个场景
使用同一硬件结构、同一位流；场景切换只加载该场景由训练集产生的硬件精确 QAT 权重
和固定 Rx 缓存。第 3 单元格未通过前，不得把软件整数参考称为实板结果。
